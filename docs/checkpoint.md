# Шпаргалка на чекпоинт

Всё, что здесь написано, проверено прогоном 2026-09-04 после исправлений. Цифры можно называть вслух.

---

## 0. Решение одной фразой

> Роутер выплат: 14 hard-правил отсекают недопустимых провайдеров, 13 целей с весами из YAML
> выбирают лучшего из оставшихся, при отказе — следующий по рангу, потом fallback на self-provider.
> Каждое решение объясняется по пунктам, отчёт даёт рекомендации с конкретным параметром
> и диагностирует сам скоринг.

Ключевая мысль для экспертов: **hard и soft разделены физически**, все 7 стратегий ТЗ — это цели
с весами, а чистый каскад — частный случай (`cascade_priority: 1.0`).

### 1.7. Таймаут: две модели (45 с)

```

ruby -Ilib bin/payout_router explain op_101 --simulation conversion --seed 6 --timeout hold
```

Одна и та же заявка: `cascade` (буква ТЗ) уводит её на payflow, `hold` (разъяснение экспертов)

Говорить: «ТЗ и ваш ответ на созвоне расходятся, поэтому семантика вынесена в параметр.

повтор у соседа — это ставка на то, что первая попытка не ушла. Сдаём `cascade` по букве ТЗ,
но хотим услышать, что правильнее».

### 1.8. Что делать, когда цель недостижима (45 с) — критерий 3 жюри, 4 балла

В таблице `route` рядом с целью из снимка стоит достижимая:

```
провайдер  заявок  доля   цель  откл.  дост.цель  откл.дост
vipay           4  40.0%  40%   +0.0   22.5%      +17.5
payflow         3  30.0%  35%   -5.0   25.2%      +4.8
quickpay        3  30.0%  25%   +5.0   52.4%      -22.4
```

Говорить: «Достижимая цель — это доля, которую провайдер получил бы при идеально пропорциональном
роутинге: на каждой заявке 100% делятся между теми, кто вообще проходит hard-правила. Видно, что
на этих данных бумажные цели внутренне противоречивы — quickpay структурно может взять половину
трафика при цели 25%, а vipay при цели 40% пропорционально причитается 22.5%. Отклонение от бумажной
цели у нас 10 п.п., и это красиво, но честная картина — вот эта вторая пара колонок».

Дальше — что с этим делать:

```
ruby -Ilib bin/payout_router compare --synthetic 200 \
  --policies config/policy.yml config/policies/attainable_shares.yml
```

«`share_targets: attainable` включает пересчёт прямо в скоринге: долю выбывшего делят оставшиеся
пропорционально своим целям. И то же число уходит в рекомендацию — `traffic_percentage` предлагается
снизить не на глазок, а до достижимого значения».

показываем колонкой `с_выбором%` — на потоке она 1.7%. Поэтому мы сделали сценарий, где выбор
есть всегда, и вклад стратегии видно в чистом виде».

### 1.10. Ничего не теряем на битом входе (20 с)

```
ruby -Ilib bin/payout_router route --queue битая_очередь.json --on-invalid skip
```

Говорить: «По умолчанию неразобранная заявка останавливает прогон с адресным сообщением — молча
отроутить половину очереди хуже, чем громко не отроутить ничего. Но за час до стопкода нужен файл,
поэтому есть `--on-invalid skip`: битые заявки уходят в карантин с предупреждением в stderr,
остальные маршрутизируются. Подсказку про этот флаг печатает само сообщение об ошибке».

## 2. Кто за что отвечает — карта для вопросов «где это в коде»

| Слой | Файлы | Одна фраза |
|---|---|---|
| Вход | `lib/payout_router/inputs/` | Читает и валидирует `providers.json`, очередь, историю, политику. Ошибка всегда с адресом: файл → провайдер → поле. Валюта — из поля или из имени шлюза (`RUB_SBP_WITHDRAW` → RUB) |
| Домен | `lib/payout_router/domain/` | `Provider`, `Operation`, `Policy` — неизменяемые `Data`-объекты |
| Hard-правила | `lib/payout_router/constraints/` | 14 классов «можно ли вообще». Реестр — `registry.rb`; `STATIC` — те, что применяются к fallback |
| Состояние | `lib/payout_router/state/` | `Ledger` — виртуальные часы и очередь сеттлментов; `ProviderState` — обороты, in-progress, интенсивность, предохранитель |
| Цели | `lib/payout_router/strategies/` | 13 классов «насколько хотим». Каждый возвращает сигнал 0..1 + текстовое примечание |
| Модель одобрения | `lib/payout_router/analytics/approval_model.rb` | Заявленная конверсия → история провайдера → пара провайдер × банк; каждый уровень усаживает предыдущий. Одна модель для `conversion`, `bank_affinity`, `expected_value`, бэктеста |
| Скоринг | `lib/payout_router/scoring/` | `CompositeScorer` — нормировка по пулу + взвешенная сумма; `ChainScorer` — цепочка ярусов; `TieBreaker` — правило при равенстве |
| Роутинг | `lib/payout_router/routing/router.rb` | Отсев → ранжирование → отправка → отказ? следующий → fallback (только статические правила). Коды причин в `reasons.rb` |
| Аналитика | `lib/payout_router/analytics/` | Отчёт, бэктест, Monte-Carlo, сравнение политик, подбор весов, 13 правил рекомендаций, `goal_activity` |
| Выход | `lib/payout_router/output/` | JSON решений, JSON отчёта, HTML-дашборд, разбор одной заявки |

**Как добавить новое правило/цель:** класс-наследник `Base` → строка в реестре → ключ в
`config/policy.yml`. Провайдер — просто запись в `providers.json`. Без правки логики роутера.

**Ещё сильнее:** цель можно добавить вообще без Ruby — декларативно в YAML (`custom_goals`:
по полю провайдера, таблицей, таблицей провайдер×банк) или плагином в `config/plugins/`.

## 4. Острые вопросы — и что отвечать

### 4.1. Где мы сильны (отвечать уверенно)

**«Что если провайдер откажет?»**
Каскад: следующий по рангу, потом fallback на `spacepayments`. В `attempts` видна вся
последовательность. Показать `route --simulation conversion --seed 7` — там каскад реально
срабатывает.

**«Что если цели противоречат?»**
Веса + `tie_breakers: [priority, conversion, name]` + `breakdown` в каждом решении.
Недостижимая цель видна в `target_attainability`, правило `share_shortfall` предлагает
снизить цель или расширить фильтр. Пресет `turnover_pressure` — конфликт из ТЗ вживую.

**«Почему веса означают то, что написано?»**
Оценки целей нормируются по пулу кандидатов заявки: лучший 1, худший 0. Без этого конверсия
(0.79–0.91) весила бы в 22 раза меньше долей (0–0.9) при равных весах. Это классический SAW
(simple additive weighting). Режим `absolute` тоже есть — одной строкой.

**«Не переобучились ли на 100 записях?»**
Усадка к приору: заявленная конверсия стоит 10 наблюдений, конверсия провайдера — 5; пара
провайдер × банк только от 5 наблюдений; leave-one-out в бэктесте. Никаких нейросетей —
чистый подсчёт частот, проверяется руками.

**«Вы нашли, что payflow заявляет 0.91 при реальных 0.47. Почему роутер верит 0.91?»**
Уже не верит: стратегия `conversion` берёт откалиброванное значение —
(9 одобрений + 10 × 0.91) / (19 + 10) = **0.62**. В `explain` это видно строкой
`conversion_24h 0.91, history 19 ops → calibrated 0.624`. Отчёт с интервалом Уилсона остаётся
инструментом аудита партнёра.

**«А если валюта не рубли?»**
Hard-правило `currency`: заявка в USD не уйдёт в RUB-шлюз ни к кому, включая fallback —
`currency_mismatch` с деталями. Валюта провайдера — из `providers.json` или из имени шлюза.

**«Как добавить провайдера / правило?»**
Провайдер — запись в JSON. Правило — класс + строка в реестре + ключ в YAML.
Или вообще без кода — декларативной целью в YAML.

**«Почему в сдаче все заявки approved?»**
Режим `optimistic` — детерминированный. Эталонные кейсы жюри требуют единственного
допустимого провайдера, случайные отказы их сломали бы. Каскад отказов показываем
в режиме `conversion` и в Monte-Carlo.

**«Что при плотной очереди / всплеске?»**
50 заявок в одну секунду → 0 без маршрута: к self-provider применяются только статические
правила допуска, его ёмкость не ограничивает. Есть регресс-тест.

### 4.2. Где нас всё ещё могут пробить — честные ответы

**«Отключите traffic_share и покажите, что изменится»** — теперь на это есть прямой ответ.

Правда: на публичной очереди — 2 решения из 10, и даже на 2000 обычных заявок обнуление
`traffic_share` и `volume_share` (40% веса) меняет Σ|откл| с 39.3 на 39.4. Это мы проверили сами.

Ответ: «Потому что на таких данных выбирать почти не из чего: у большинства заявок после
hard-правил остаётся один допустимый провайдер — мы это меряем колонкой `с_выбором%`, на потоке
она 1.7%. Аблацией на данных без выбора нельзя показать ничего. Возьмите сценарий `open_field`,
где все трое допустимы в каждой заявке: там роутер попадает в цели **точно, Σ|откл| = 0.0**,
а без целей по долям — **68.7 п.п.** Вот вклад стратегии, измеренный там, где он вообще может
проявиться». Показать `payout_router stress --scenario open_field open_field_no_shares`.

**«Ваш бэктест говорит, что balanced хуже фактического роутинга»**
Правда: −5.0%, переставляя 57 заявок из 100.

Ответ: «Да, и это осознанный размен. `balanced` оптимизирует не одобрения, а соблюдение
обязательств перед партнёрами. Если бизнесу нужны одобрения — `conversion_first`, +4.7%.
Мы показываем обе точки и цену перехода — в этом смысл `compare`». **Заранее решить, какую
политику сдаём** (см. вопросы экспертам, п. 7).

**«Покажите, как работает предохранитель на этой очереди»**
Правда: на 10 заявках не срабатывает почти никогда, в `optimistic` — вообще.

Ответ: «Он для продовых объёмов. Показываю на 200 заявках в режиме `conversion`».
Не выдавать за живую фичу демо.

**«Проверяющий скрипт считает допустимость статически, а у вас состояние копится»**
Правда: наш пул ⊆ пула валидатора, поэтому «выбран недопустимый» невозможен, но на плотной
очереди мы можем увести заявку на fallback там, где статический скрипт ждал бы внешнего.

Ответ: «Мы моделируем то, что происходит на самом деле: заявка занимает реквизит и слот
до ответа провайдера. Валидатор это не учитывает — но и не штрафует: fallback в его списке
допустимых». На публичной очереди (шаг 30 с) расхождений нет.

### Что поменяли в коде после созвона

**1. Таймаут — две модели (30:22).** Эксперт: «при тайм-ауте считается, что всё прошло успешно»
и «освобождение коэффициентов из каскада — только после получения статуса от провайдера».
Это **противоречит букве ТЗ** («при отказе/таймауте — исключить провайдера из пула и выбрать
следующего»), поэтому мы реализовали обе семантики и переключаем их параметром `simulation.timeout`:

- `cascade` — как в ТЗ, режим по умолчанию и режим сдачи;
- `hold` — заявка остаётся за провайдером (`simulated_result: expired`), повторной отправки нет,
  слот in-progress и реквизит не освобождаются. В дневной оборот сумма не идёт: подтверждения
  не было, а `in_progress_amount` её уже держит — иначе получилось бы двойное списание ёмкости.

Демо на одной заявке: `explain op_101 --simulation conversion --seed 6 --timeout cascade` уводит её
на payflow, `--timeout hold` оставляет на vipay с пометкой `timeout without provider status`.

Зачем это важно сказать вслух: **`hold` — единственная модель, которая не может привести к двойной
выплате**. Если провайдер не ответил, повтор у соседа — это ставка на то, что первая попытка не ушла.

**2. Внешний снимок состояния перед каждой операцией (22:36).** Эксперт: система может передавать
обновлённое состояние провайдеров перед каждой операцией, а накопление счётчиков роутером — это
оптимизация. Раньше мы умели только второе. Теперь `POST /route` принимает конверт:

```json
{ "operation": { "operation_id": "op_1", "amount": 15000, "bank": "sberbank" },
  "providers": [{ "payment_system": "vipay", "in_progress_count": 9, "status": "inactive" }] }
```

Присланные ёмкостные счётчики перетирают наши, остальные поля обновляют конфигурацию провайдера —
через это же работает сценарий «провайдер выключился посреди очереди». Неизвестное имя поля — ошибка
400 с адресом, а не молчаливое игнорирование: иначе роутер считал бы по устаревшим данным.

**3. YJIT (29:00).** Эксперт: считать надо максимально быстро, в Ruby есть способы ускорения.
`bin/payout_router` включает YJIT там, где он собран (официальный `ruby:4.0` — да, RubyInstaller
под Windows — нет, поэтому включаем по факту наличия, а не по версии).

### Атомарность и точка линеаризации (24:43, 27:22) — здесь мы отвечаем сильнее всего

Эксперты описали ровно ту модель, которая у нас уже была; на чекпоинте это стоит назвать их словами:

- **точка линеаризации — `Ledger#dispatch!`**: в момент отправки заявка занимает слот in-progress,
  сумму in-progress, реквизит и отметку интенсивности. Дальше по каскаду этот провайдер уже
  «занят» — конкурировать за ту же ёмкость две заявки не могут;
- **при отказе резерв откатывается**: `ProviderState#settle!` возвращает слот, сумму и реквизит,
  а в дневной оборот отказ не попадает. Отметку интенсивности не откатываем сознательно: запрос
  к провайдеру был сделан, он честно занял минутное окно;
- **освобождение — по ответу, а не сразу**: ответ приходит через `avg_latency_sec`, до тех пор
  заявка висит in-progress. Это виртуальные часы `SettlementQueue`, а не мгновенные счётчики.

## 4.5. Стресс-прогон: чем мы проверяем, что решение действительно работает

```
bundle exec rake stress
```

17 сценариев давления через тот же конвейер, что и сдача, ~16 000 заявок. Ключевая мысль
для экспертов: **проверки двух разных сортов, и мы их не путаем.**

- **Инварианты** — обязаны держаться при любом давлении: ни одной потерянной заявки, ровно одна
  `selected`-попытка на заявку, ёмкость сходится (каждая отправка закрыта ответом, всё занятое
  возвращено), выбранный провайдер действительно принимает эту заявку, пики in-progress
  и интенсивности не выше лимитов. Пики считаются в момент отправки, а не по итогу: к концу
  очереди in-progress рассасывается, и нарушение из финальных чисел не видно.
- **Метрики** — измеренные числа без порогов. Мы не пишем «ожидаем fallback < 10%», потому что
  такой тест проверял бы наше ожидание, а не поведение.

**Если спросят «а ваши тесты вообще что-нибудь ловят».** Каждый пример проверен мутацией:
в код вносилась настоящая ошибка — не возвращать слот при отказе, снять сортировку очереди
по времени, сдвинуть границу `limit_amount_max` на 1 ₽ — и тест обязан был упасть. Первая версия
набора три из этих мутаций **не поймала**, и её переписали: проверки, читавшие счётчики роутера,
заменены на пересчёт заново по решениям и снимку. Проверка, опирающаяся на ту же бухгалтерию,
которую она проверяет, подтверждает сама себя.

Что стресс-прогон нашёл — это и есть главный аргумент, что он не декоративный:

**0. Цели по долям действительно решают — но доказать это можно только там, где есть выбор.**
Это ответ на самый неприятный вопрос к нам: «отключите `traffic_share` и покажите, что изменится».
Раньше ответить было нечем — на обычных данных ничего не менялось. Теперь есть сценарий
`open_field`, где все три провайдера допустимы в **каждой** заявке (банк из общего списка, сумма
в пересечении диапазонов, ёмкость с запасом). Там роутер попадает в целевые доли **точно:
Σ|откл| = 0.0**. Тот же прогон с весом 0 у `traffic_share` и `volume_share` — **68.7 п.п.**

Почему на обычных данных этого не видно: колонка `с_выбором%` показывает, в скольких заявках
после hard-правил остался больше чем один кандидат. На `flood` это 1.7%, на `single_bank` — 0%.
Там распределение определяют банковские фильтры и потолки чека, а не скоринг, и аблацией
по весам не докажешь ничего. Это честная граница применимости нашей же метрики.

**1. Формула дневного лимита из ТЗ переливает через лимит.** `daily_approved_amount + amount <=
daily_amount_limit` считает только подтверждённый оборот, а он растёт лишь по ответу провайдера.
Пока провайдер молчит, следующие заявки проходят проверку по устаревшему числу. Сценарий `flood`
(3000 заявок) даёт **103% дневного лимита**. Мы добавили правило `daily_limit_reserved` —
«оборот + in-progress + сумма ≤ лимит», то самое резервирование, о котором говорили эксперты
на созвоне. Тот же поток с ним: **99.4%**.

Почему не сдаём его по умолчанию: автопроверка организаторов считает допустимость по формуле ТЗ.
С резервированием payflow (оборот 2.9 млн + 120 тыс. в обработке против лимита 3 млн) выпадает
целиком, и эталонный кейс op_107 уходит на self-provider. Это зафиксировано отдельным тестом,
чтобы цена была видна. **Вопрос экспертам — какое поведение они считают правильным.**

**2. Залп в одну секунду self-provider принимает с перегрузкой.** 500 заявок в одну секунду:
внешние кончаются мгновенно, и fallback берёт на **467 заявок больше**, чем у него реквизитов.
Ёмкость его не ограничивает по замыслу — иначе заявка осталась бы без маршрута, — но глубину
перегрузки мы показываем числом, а не прячем.

**3. Внешний снимок счётчиков мог увести in-progress в минус.** Если вызывающая система присылает
свежие счётчики (`Ledger#sync!`), а ответы на заявки, отправленные до снимка, продолжают вычитать,
счётчик уходит ниже нуля. Освобождение ёмкости теперь не опускается ниже нуля; без `sync!`
ограничение не срабатывает никогда — каждая отправка закрывается ровно одним ответом,
и это проверяет инвариант сохранения.

**4. Отклонение от целей надо читать правильно.** В сценариях с исчерпанной ёмкостью Σ|откл|
90+ говорит не о стратегии, а о том, что лимитов физически не хватило. На `share_pressure`
со свободной ёмкостью пропорционально доступности vipay причитается 21.4%, payflow 12.7%,
quickpay 58%, а роутер даёт **29 / 22.4 / 40.7** — то есть дожимает доли к целям 40/35/25,
насколько позволяют hard-правила.

  Аблация по одной цели: только `traffic_share` меняет 2 решения из 10, остальные — 0. Причина в данных:

- **При двух кандидатах нормировка по пулу делает каждую цель бинарной (0/1)** — решение сводится
