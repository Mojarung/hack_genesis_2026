# analysis — разведка данных на polars

Отдельный от решения инструмент: считает статистику по `data/`, чтобы понять,
как устроены данные кейса, и найти нестыковки. **Решение задачи здесь не живёт** —
роутинг пишется на Ruby, как требует ТЗ. Этот каталог — блокнот аналитика,
результаты его работы записаны в `docs/data_audit.md`.

## Запуск

```powershell
cd analysis
uv sync                             # один раз
uv run python audit_providers.py    # снапшот провайдеров: поля, лимиты, банки, ёмкость
uv run python audit_history.py      # история: качество, конверсия, латентность, интенсивность
uv run python audit_queue.py        # очередь + сверка с эталоном + потолки долей
uv run python audit_decisions.py    # формат ответа и контракт валидатора
```

## Что внутри

| Файл | Назначение |
|---|---|
| `paylens/loaders.py` | единственное место, где зашиты пути к `data/`; загрузка в polars |
| `paylens/rules.py` | реплика hard-constraints из `scripts/validate_10.rb` — сверена с эталоном организаторов, расхождений 0 |
| `audit_*.py` | сами проходы, каждый печатает разделы в stdout |

`paylens/rules.py` полезен не только для аудита: это проверенная и читаемая
спецификация того, как валидатор понимает hard-фильтры. Ruby-реализация должна
давать те же коды причин в том же порядке.

## Договорённость

Скрипты только читают `data/` и печатают в stdout. Ничего не пишут в корень
репозитория и не участвуют в сборке ответа — `routing_decisions_test.json` и
`routing_report_test.json` формирует Ruby-код.
