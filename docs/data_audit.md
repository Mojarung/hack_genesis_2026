# Аудит данных кейса «Умный роутинг выплат»

Проход по каждому файлу из `data/` + `scripts/validate_10.rb`. Всё, что здесь
написано, посчитано скриптами из `analysis/` (polars) и воспроизводимо:

```powershell
cd analysis
uv run python audit_providers.py    # снапшот провайдеров
uv run python audit_history.py      # история операций
uv run python audit_queue.py        # очередь + эталон
uv run python audit_decisions.py    # формат ответа + контракт валидатора
```

`analysis/paylens/rules.py` — реплика hard-constraints валидатора на Python.
Она **сошлась с эталоном организаторов на 100%** (eligible-списки,
детерминированные кейсы, коды skip для всех 10 заявок), поэтому дальше
используется как проверенная спецификация правил.

Краткая версия «что где лежит» — в `docs/data.md`. Здесь — подробности.

(то есть нужен fallback), — **ноль**.

### Во что упирается распределение

Это самое важное для стратегии. Считаем, что провайдер может взять только те
заявки, которые проходят его hard-фильтр:

| provider | потолок доли по count | цель | пол по count | пол по объёму | потолок по объёму |
|---|---:|---:|---:|---:|---:|
| vipay | 40% (4 из 10) | 40% | 0% | 0% | 26% |
| payflow | 40% (4 из 10) | 35% | 10% | 0% | 27% |
| quickpay | 90% (9 из 10) | 25% | **30%** | **51%** | 100% |

- **У vipay нулевой запас**: его потолок ровно равен цели. Чтобы выйти на 40%,
  он обязан забрать все четыре доступные ему заявки. Любая «умная» уступка
  конкуренту уводит vipay ниже цели.
- **Цель quickpay недостижима**: три заявки (op_103, op_104, op_108) больше
  никому не подходят, это 30% по количеству и 51% по объёму при цели 25%.
  Ровно тот случай, за который дают баллы: «определено поведение системы, если
  текущую цель выполнить невозможно».
- Цель по объёму на этой очереди тем более неисполнима: vipay физически не может
  взять больше 26% денег, payflow — больше 27%.

Чистый каскад по `priority`, без всяких soft-целей, даёт:

| provider | каскад | цель | заявки |
|---|---:|---:|---|
| vipay | 40% | 40% | op_101, op_105, op_106, op_109 |
| payflow | 30% | 35% | op_102, op_107, op_110 |
| quickpay | 30% | 25% | op_103, op_104, op_108 |

Это распределение **совпадает с `sample_routing_decisions.json`** — образец
организаторов и есть чистый каскад. И оно уже почти оптимально: суммарное
отклонение от целей 10 п.п., а лучше на этой очереди не сделать никак (см. потолки
выше). Отсюда важное следствие: **на публичной очереди умный роутер не может
заметно обогнать наивный каскад по метрике долей** — выигрывать надо на объяснимости,
работе со стейтом, конверсии и на боевой очереди, где потолки будут другими.

При каскаде payflow доходит до 99.6% дневного лимита (2 988 800 из 3 000 000),
остаток 11 200 ₽. Следующая же заявка на payflow дороже 11 200 ₽ уйдёт другому —
но только если роутер обновляет стейт. Валидатор этого не заметит, эксперты — да.

## 4. `reference_decisions.json` — эталон организаторов

Три секции: `deterministic_cases` (4 кейса), `eligible_providers` (все 10 заявок),
`skip_reasons_expected` (9 заявок, для op_101 отсева нет).

Наш независимый расчёт сошёлся с эталоном полностью:

- eligible-списки — 0 расхождений на 10 заявках;
- все 4 детерминированных кейса действительно имеют единственного внешнего
  провайдера;
- коды skip совпали для всех заявок, лишних и недостающих нет.

Единственная нестыковка — `spacepayments` в эталонных `eligible_providers` не
упоминается ни разу, хотя функция `eligible_providers` внутри самого валидатора
его в списки включает. На проверку это не влияет (валидатор проверяет вхождение
выбранного провайдера в свой собственный список, а не совпадение со списком из
эталона), но читать эталон как «вот все допустимые» нельзя.

## 5. `sample_routing_decisions.json` — образец ответа

- Поля решения: `operation_id`, `selected_provider`, `attempts`,
  `simulated_result`, `latency_sec`. Поля попытки: `provider`, `decision`, `reason`.
- **Поля `details` в образце нет**, хотя в примере из ТЗ оно есть. Валидатор его
  не требует.
- `simulated_result` = `approved` во всех 10, `latency_sec` = 30 во всех 10.
  То есть в образце ни исход, ни латентность не симулируются вообще, хотя ТЗ
  прямо предлагает симулировать по `conversion_24h`.
- Словарь причин: `selected` → `first_eligible` (6), `only_eligible_provider` (4);
  `skipped` → `bank_not_in_list` (8), `amount_exceeds_limit` (3),
  `amount_below_minimum` (2).
- Распределение образца: vipay 4 (40%), payflow 3 (30%), quickpay 3 (30%).
  А в примере отчёта в ТЗ распределение другое: vipay 2 (20%), payflow 2 (20%),
  quickpay 6 (60%). Один из них иллюстративный, но какой — по документу не понять.

### `attempts` — это не хронология

В четырёх решениях `selected` стоит **не последним**:

```
op_105: vipay:selected -> payflow:skipped
op_106: vipay:selected -> payflow:skipped
op_107: vipay:skipped  -> payflow:selected -> quickpay:skipped
op_109: vipay:selected -> payflow:skipped
```

Каскад, выбрав vipay на op_105, до payflow физически не доходит. Значит, в
образце `attempts` — это **полный разбор всех кандидатов в порядке `priority`**,
а не журнал реальных попыток. Это прямо противоречит критерию жюри «сохранена
последовательность рассмотрения провайдеров и повторных попыток» (2 балла).

При этом формат такой не случаен: валидатор ждёт запись `skipped` для каждого
провайдера из `skip_reasons_expected`, включая тех, до кого честный каскад не
дошёл бы. Иначе — предупреждение. То есть **перечислять всех отсеянных
обязательно**, даже если выбор случился раньше.

Ещё образец не показывает eligible-, но не выбранных провайдеров: на op_101
допустимы все трое, а в `attempts` только vipay. Почему проиграли payflow и
quickpay — из ответа не видно, а за это дают 4 балла («понятно, почему другие
рассматриваемые провайдеры были исключены»).

`spacepayments` в `attempts` образца не встречается ни разу.

## 6. `validate_10.rb` — фактическая спецификация приёмки

Обязательные поля: решение — `operation_id`, `selected_provider`, `attempts`;
попытка — `provider`, `decision`, `reason`. `decision` строго из
`{selected, skipped}`, любое третье значение — ошибка структуры.

**Проверяется жёстко (ошибка → exit 1):**

1. все `operation_id` из очереди покрыты;
2. структура полей;
3. `deterministic_cases`: `selected_provider` совпадает с эталоном;
4. `selected_provider` входит в eligible-список, посчитанный самим валидатором.

**Проверяется мягко (предупреждение):** для каждого провайдера из
`skip_reasons_expected` есть попытка с `decision = "skipped"`; лишние
`operation_id`.

**Не проверяется вообще:**

- текст `reason` — сверяется только сам факт `skipped`;
- `simulated_result` и `latency_sec` — валидатор их не читает;
- порядок `attempts` и то, что `selected` стоит последним;
- что помеченный `skipped` провайдер действительно недопустим;
- обновление стейта между заявками — eligible считается по статическому снапшоту;
- лишние поля в решении и в попытке — игнорируются;
- `requests_per_minute_limit` — поля в данных нет, проверки нет.

Два следствия, важных для реализации:

- **Можно честно показывать и цепочку попыток, и проигравших конкурентов.**
  Третьего значения `decision` завести нельзя, но eligible-но-проигравшего
  допустимо пометить `skipped` со своей причиной (например, `lower_score`) и
  положить рядом произвольные поля (`score`, `details`). Валидатор это примет,
  а объяснимость выиграет. Риск: неизвестно, будет ли боевой скрипт строже.
- **`spacepayments` проходит eligible-проверку всегда** (в валидаторе явное
  исключение по имени для провайдера с `traffic_percentage = 0`). Формально им
  можно закрыть любую заявку, но на четырёх детерминированных кейсах это
  немедленная ошибка. Fallback должен включаться строго по факту пустого пула
  внешних провайдеров.

## 7. Нестыковки — что спросить у организаторов

Пронумеровано, чтобы можно было кинуть в чат списком.

1. **`attempts` — журнал попыток или разбор кандидатов?** В образце `selected`
   в четырёх случаях стоит не последним (op_105, op_106, op_107, op_109), то есть
   перечислены и те провайдеры, до которых каскад не дошёл. Критерий жюри при
   этом требует «сохранена последовательность рассмотрения и повторных попыток».
   Какой из двух вариантов правильный?
2. **Можно ли помечать `decision: "skipped"` провайдера, который прошёл
   hard-фильтр, но проиграл по стратегии** (причина вида `lower_score`)?
   Или `skipped` зарезервировано под hard-отсев, а проигравших показывать не надо?
   Третьего значения `decision` валидатор не допускает, а объяснимость выбора
   оценивается отдельно.
3. **Нужно ли поле `details` в `attempts`?** В примере ТЗ оно есть, в
   `sample_routing_decisions.json` его нет, валидатор не требует.
4. **Как оценивается `simulated_result` и `latency_sec`?** Валидатор их не
   читает, в образце это константы `approved` / 30. Симулировать по
   `conversion_24h`, или можно калибровать по истории (там `expired` отличается
   от `approved` латентностью в 5–10 раз)?
5. **`conversion_24h` payflow = 0.91, а по истории 0.474** (9 approved из 19,
   95% ДИ [0.273, 0.683] — заявленное значение вне интервала; у vipay и quickpay
   расхождения статистически незначимы). Какое значение считать правдой и на что
   опираться стратегии «приоритизация по конверсии»?
6. **29 из 100 строк истории невозможны при текущем `providers.json`** — все по
   `bank_not_in_list` (vipay 20, payflow 9; например `op_001`: vipay + alfa,
   хотя у vipay `banks: [sberbank, tinkoff, vtb]`). Это специально — история
   снята до смены конфигурации, или ошибка генерации данных?
7. **Цель quickpay 25% недостижима**: три заявки публичной очереди (op_103,
   op_104, op_108) не проходят ни к кому, кроме него, — это 30% по количеству и
   51% по объёму. Аналогично vipay может взять максимум 4 заявки при цели 40%,
   то есть запас нулевой. `traffic_percentage` — это цель, к которой стремимся
   при прочих равных, или обязательство, отклонение от которого штрафуется?
8. **Изменится ли `providers.json` к тестовой очереди** (новый снапшот на другой
   момент времени) или он останется тем же?
9. **Что ждать в `operations_queue_test.json`:** будет ли заполнен `card_brand`,
   появятся ли реквизиты не `sbp` (карта), новые банки вне известных шести, новые
   провайдеры? Нужна ли устойчивость к операции, которую не берёт вообще никто?
10. **Будет ли `reference_decisions` для тестовой очереди** — то есть будут ли в
    ней детерминированные кейсы, по которым сверяется конкретный провайдер?
11. **`daily_approved_amount` payflow = 96.7% лимита на 09:00.** Считать это
    статикой на всё окно обработки очереди, или сторонний трафик продолжает
    расходовать лимит параллельно?
12. **`requests_per_minute_limit` в данных нет**, а в hard-constraints он есть.
    Значения задавать самим? Наблюдаемый поток истории — около 1 заявки в минуту,
    пик 3, то есть пример из ТЗ («7/мин на терминал») никогда не сработает.

## 8. Что данные диктуют архитектуре

Не проектирование решения, а список требований, который выпал из аудита.

**Расширение вширь — то, чего в данных сегодня нет, а завтра будет:**

- Новый провайдер добавляется как строка в `providers.json` — код не должен знать
  имён провайдеров. Единственное имя, которое придётся зашить, — `spacepayments`
  как self-provider, и то лучше через конфиг (`fallback_provider: spacepayments`).
- Новое hard-ограничение (`requests_per_minute_limit`, `daily_turnover_max`)
  добавляется как ещё одна независимая проверка с собственным кодом причины,
  а не как ветка в общей лестнице `if`. Порядок проверок влияет на то, какую
  причину увидит эксперт, — он должен быть явным и настраиваемым.
- Новая soft-цель добавляется как ещё один скорер с весом. Стратегий в ТЗ семь,
  и требуется их комбинация — значит, это не `case strategy`, а взвешенная сумма
  нормированных оценок.
- Новые банки и новые виды реквизитов: `bank` — открытое множество слагов,
  `payout_requisite` — мапа с одним ключом-видом. Ни то, ни другое нельзя
  зашивать перечислением.

**Расширение вглубь — то, что должно быть настраиваемым без правки логики:**

- веса soft-целей и правило разрешения конфликтов между ними;
- границы бакетов сумм для стратегии «по диапазону чека»;
- источник конверсии: поле снапшота, история, смесь — и параметры сглаживания;
- параметры симуляции исхода и латентности;
- недостающие поля провайдеров (`volume_share_pct`, `requests_per_minute_limit`,
  `daily_turnover_min/max`) — задавать в своём конфиге поверх снапшота, **не
  правя `providers.json`**: организаторы пришлют свою версию файла.

**Обязательные части, которые видно из данных:**

- **Изменяемый стейт провайдера** отдельно от снапшота: `daily_approved_amount`,
  `in_progress_*`, окно интенсивности обновляются после каждой заявки. На
  публичной очереди это видно на payflow (99.6% лимита к концу).
- **Журнал решения**, в который пишется каждый рассмотренный провайдер: выбранный,
  отсеянные по hard-фильтру (обязательно все — иначе предупреждения валидатора)
  и проигравшие по скорингу с числами.
- **Fallback на `spacepayments`** строго по факту пустого пула внешних.
- **Симулятор исхода и латентности**, откалиброванный по истории: исход из
  конверсии, латентность из распределения своего класса (approved/rejected 5–119 с,
  expired 327–859 с).
- **Отчёт**: фактические доли против целей, отклонения и их причины, использование
  лимитов, рекомендации с конкретным параметром.
- **Обработка граничных случаев**, которые данные уже показывают: `null` в любом
  лимите = «ограничения нет»; пустой `banks` = «любой банк»; заявка ниже минимума
  всех провайдеров; заявка выше максимума всех; неизвестный банк; провайдер с
  `traffic_percentage = 0`, не являющийся self-provider (по логике валидатора он
  выбывает совсем).

**Чего делать не надо:**

- выводить hard-ограничения из истории — она снята при другой конфигурации банков;
- считать `conversion_24h` из снапшота истиной без оговорки (payflow);
- оптимизировать доли на публичной очереди — там потолок уже почти достигнут
  наивным каскадом, выигрыш будет в другом;
- хардкодить `operations_queue_10.json` — боевой файл будет называться иначе.
